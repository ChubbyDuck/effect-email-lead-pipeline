# Deployed pipeline E2E cases

Run `pnpm test:e2e:floci` (the CDK stack) or `pnpm test:e2e:alchemy` (the Alchemy stack). Both run every case. All cases use Floci's real event source poller and real application entrypoints. The suite does not manually acknowledge main-queue messages. Test-only driven adapters make exceptional port outcomes reproducible.

Fourteen additional cases cover recovery after two transient failures of Inbox read/store and Sources read/publication, failures of the final delete for Inbox and Sources, all attachment stores failing, configuration failures in all three handlers, defects of the final delete, the Inbox rejected-input deletion defect, and shutdown after one sibling succeeds. Configuration failures reach the corresponding DLQ before any port attempt; both messages in a Leads configuration-failure batch are dead-lettered. A failure of the final delete leaves only the input of that stage while downstream work completes. Typed delete failures are logged as warnings and acknowledged; defects fail the invocation and reach the stage DLQ. A rejected Leads invocation dead-letters its entire delivered batch even if a sibling already succeeded.

Every case checks that all main queues drain and each DLQ grows by exactly the expected number. Dead-letter assertions inspect messages without deleting or redriving them. Setup, per-DLQ assertions, and teardown verify the absence of DLQ consumers. The synthesized stack also asserts no mapping targets any DLQ.

This matrix describes distinct pipeline outcomes. Detailed domain/schema, duplicate-record, concurrency, and retry-boundary variants remain covered by unit and adapter integration tests. The E2E bundles replace the order repository with a test adapter. The production order repository writes each order to DynamoDB with a conditional put on its idempotency key, and it does not submit an order to an external system.
